# Norr 原生应用

macOS 应用标识为 `app.norr.mac`，Windows 为 `app.norr.windows`，Android 为 `app.norr.mobile`，iOS 为 `app.norr.ios`。四端共用 React 页面、Tauri IPC 与 Rust 车辆核心，直连厂商 REST 和原生 HTTP/2 gRPC。当前车辆服务适配中国区 Polestar 2 的 ICUP / AccountLinking 平台。

各平台当前完成度、测试包和待办汇总在[开发进展](../../docs/PROGRESS.md)。本文保留构建说明与历次验证详情。

共用登录页已增加「短信登录 / 密码登录」切换，密码登录使用中国大陆手机号与 Polestar 账号密码。四端通过同一 Rust 核心调用厂商接口，成功后沿用系统加密会话保存、续期及车辆读取。密码字段在提交结束、切换方式和取消时清空。此功能已随 `v0.1.0-alpha.3` 发布，真实密码登录与重启恢复待验证。

`alpha.3` 和 `alpha.4` 存在密码命令 ACL 漏项，会报 `Command sign_in_password not allowed by ACL`。`alpha.5` 已补齐权限并通过 Windows 原生权限回归测试。Windows 滑块回调同时改用官方 webview 消息模式，验证成功后继续发送短信，实际短信与密码登录结果待新版实机复测。

## iOS 模拟器版

首版面向 Apple Silicon Mac 上的 iPhone 模拟器，最低部署版本为 iOS 15.0。复用五个主页面与本地车辆核心，随包携带界面、字体和 P2/P4 素材。模拟器构建使用独立的 iOS 数据目录和钥匙串。

Swift 系统桥接已接入官方短信验证 WKWebView、设备身份确认、系统通知与点击返回、JSON 备份选择、CSV/JSON 文件导出和外部地图。采集在前台运行，返回应用时按偏好刷新。短信验证码可由另一部手机接收后填入。

在安装完整 Xcode 与 iOS Simulator 运行时的 Mac 上，从仓库根目录构建。中国区登录配置继续由 `NORR_POLESTAR_CN_SIGNING_KEY` 或 `.env.secrets` 读取。

```sh
npm ci
rustup target add aarch64-apple-ios-sim
npm run build:ios
```

`build:ios` 默认生成 ARM64 模拟器的 release 构建，归档后生成 `target/ios/Norr.app` 与 `target/ios/Norr_0.1.0_ios-arm64-simulator.zip`，进行本地 ad-hoc 签名校验。模拟器钥匙串权限通过专用 `simulator.entitlements` 嵌入可执行文件，限定于模拟器链接配置；实体设备仍使用 Xcode 开发团队与设备签名。iOS 工程位于 `apps/native/src-tauri/gen/apple`，Swift 桥接位于 `apps/native/src-tauri/ios`。

### 未签名真机 IPA

在装有完整 Xcode 和 iOS SDK 的 Mac 上执行以下命令，登录配置与模拟器构建共用。

```sh
rustup target add aarch64-apple-ios
npm run build:ios:unsigned
```

产物为 `target/ios/Norr_0.1.0_ios-arm64-unsigned.ipa`，内容为 `Payload/Norr.app`。构建使用 iPhoneOS SDK，校验 ARM64 架构和 Mach-O 真机平台，移除签名与描述文件，并检查 ZIP 完整性。此步骤无需 Apple 签名证书。真机安装前需要使用有效证书与匹配的描述文件重新签名，按签名方式满足设备登记要求。重新签名后的安装、钥匙串和车辆功能待真机验证。

GitHub Release 同时提供模拟器 ZIP 与未签名 IPA，两类产物分别纳入上传校验与 `SHA256SUMS.txt`。本机连续构建两种目标时依次执行命令，它们共用 Xcode 归档目录。

在 Xcode 的模拟器窗口中启动一台 iPhone 后，从仓库根目录安装并打开应用。本机 Xcode 27.2 使用 Device Hub 提供模拟器窗口。

```sh
xcrun simctl install booted target/ios/Norr.app
xcrun simctl launch booted app.norr.ios
```

## GitHub Actions

`Checks and packages` 在 PR 和主分支代码更新时运行检查。仅文档、issue 表单与许可文件变化时跳过这类即时检查。四端打包由 `Daily alpha release` 调用。

- PR 执行前端测试、类型检查与生产构建，以及 macOS、Windows 的 Rust 格式、release 测试和严格 Clippy。
- 每天北京时间 03:20（UTC 19:20）检查 main。有上次成功发布的全平台版本之后的新提交时生成四端测试包，版本按 `v0.1.0-alpha.1`、`v0.1.0-alpha.2` 递增。提交判断包含文档更新，也会补上此前构建失败而尚未发布的提交。
- 所选平台与上次成功发布的源提交一致时，只运行提交检查任务。手动发布时，在 `Daily alpha release` 选择 main，`platform` 选 `all` 构建全部平台，选 `windows` 只构建 Windows x64。Windows 单平台发布后，每日任务仍会补齐全平台版本。
- 所选平台检查与打包全部通过后创建预发行版，上传安装包与 `SHA256SUMS.txt`，验证上传文件的 SHA-256 后发布。并发发布串行执行，上传中断后可复用同一提交、同一平台选择的草稿与版本号。
- 安装包直接附在 Release 页面，Actions 中另保留 14 天的构建产物。[Release 下载](https://github.com/pepsing/Norr/releases) · [每日发布运行](https://github.com/pepsing/Norr/actions/workflows/release.yml)

Release 的更新摘要来自所选平台上次成功发布以来的 PR 标题与直接提交的首行，合并 PR 按编号去重。关联 issue 从提交信息、PR 正文中的 `#编号` 或 issue URL，以及 PR 的关闭关联中收集，显示问题标题、链接和当前状态。首次发布另附当前功能范围说明。

版本号只在构建工作区注入，源码的基础版本由根目录 `package.json` 维护。npm、Cargo 与 Tauri 版本同步为 alpha 版本，Android versionCode 和 Apple bundleVersion 使用独立递增的构建号，从 1001 开始。相同提交的草稿重试沿用构建号。

iOS 的系统短版本使用三段数字，例如 `0.1.0`，对应 alpha 迭代由 Release 标签、安装包文件名与 bundleVersion 标识。`v0.1.0-alpha.1` 的原生构建号为 `1001`。

GitHub 定时任务可能因负载延迟，公开仓库连续 60 天无活动时定时工作流会被停用，届时可在 Actions 中重新启用。[GitHub 定时任务说明](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

## macOS 日常使用

登录启动使用 `SMAppService.mainAppService`，默认关闭。充电状态和指令结果通知默认关闭，开启时通过 macOS 申请通知权限。系统权限、用户偏好与运行状态分别显示。通知采用静默横幅与通知中心列表，展示方式受 macOS 设置和专注模式影响。
