# Norr Watch 首版需求与设计说明

日期：2026-11-17。设计版本：04，首页活动按钮与当前 Norr 对齐；空调使用默认舒适温度。原生实现已加入工程，构建与当前验收记录见 [Watch README](../../../apps/native/src-tauri/watch/README.md)。下文保留产品需求，不能将验收条件视为已完成的真机验证。

## 用户目标与范围

面向已在 iPhone 登录 Norr 的中国区 Polestar 2 车主。抬腕查看电量、续航、门锁和充电状态，在手表上解锁、锁车、开启或关闭空调。首次配置通过 iPhone 完成；完成同步后，手表在有网络且授权有效时能脱离 iPhone 使用。

设计交付包含需求、视觉稿、状态设计和 HTML 交互演示；后续已落地 SwiftUI 配套 App、Widget、手机授权同步与请求层。HTML 和原生 `--demo` 模式不读取用户账号、不请求极星服务、不发送车辆指令。所有演示车辆数值、时间和命令结果均为标记清楚的固定样例。

| 首版包含 | 行为 |
| --- | --- |
| 车辆概览 | 车图、车型、电量、预计续航、门锁状态、更新时间、手动刷新 |
| 门锁 | 查看锁态及独立更新时间；解锁、锁车均经二次确认，展示发送、回执与车辆回读 |
| 空调 | 查看座舱温度与运行状态，以默认舒适温度 22 °C 开启或关闭，查看回执与独立回读 |
| 充电 | 查看充电状态、功率、目标电量和预计剩余时间；缺失值不推算 |
| 表盘组件 | 圆形电量、矩形电量与续航；点击进入 App，首版不直接发送车控 |
| 手机配套设置 | 同步会话、当前车辆与外观，处理换账号、换车、退出登录 |
| 异常状态 | 未配置、同步中、读取中、部分数据、完全离线、会话失效、无车辆、权限不足、命令待核对 |

首版不包含尾门、车窗、鸣笛、充电计划编辑、地图和历史分析。P4 暂不作为已适配车辆展示。多车用户沿用手机选中的车辆，切车时清除上辆车的待显示状态，命令始终绑定 VIN。

## 联网和执行模型

### 主路径：手表发请求，系统选择网络

Watch App 使用原生 SwiftUI 与 URLSession。车辆请求由 Watch 执行；watchOS 可经配对 iPhone 的系统网络代理、手表 Wi-Fi 或蜂窝网络访问服务。借用手机网络不需要手机 Norr 在前台，也不经过 Norr 的 WatchConnectivity 请求转发。

应用处理请求成功、无网络、超时和授权错误。不要从 WCSession.isReachable 推断互联网是否可用，也不要将系统选路当成 App 可以强制或立即切换的功能。用户界面显示信息的新旧与操作结果，不显示未经证实的“正在通过 iPhone / Wi-Fi / 蜂窝”线路标签。

WatchConnectivity 只负责初始配置、会话同步、车辆选择、素材引用与机会性的车辆快照同步。手机 App 中转车辆请求是后备技术方案，只有直连验证失败、重新评审后才纳入；本稿不将两个执行端同时作为默认车控路径。

### 前台与后台

- 手表 App 前台可发起交互请求。离开页面、垂腕或进入后台时，不能假设现有请求和轮询会无限运行。
- 使用系统允许的后台网络与刷新任务更新缓存。后台调度可以延迟，不承诺固定分钟刷新或实时表盘。
- 表盘显示带时间的本地快照。超过产品定义的新鲜度阈值时显示缓存提示；阈值必须按数据类型定义并在技术验证中确定，不能把传输时间当成车辆上报时间。
- 请求发出后进入后台：保存请求标识、目标车辆、动作、发送时间和当前证据。重新进入时恢复待核对状态，不自动重复提交。
- 手机需要处理 WatchConnectivity 消息时可由系统在条件允许时后台唤醒，但桥接不能依赖 React 页面保持活动。

## 登录态和数据同步

布局补充约束：常规字号优先将首页、空调、门锁与充电的主要状态和操作置于一屏。首页电量区进入充电，刷新放在“更多”。大字号允许滚动，不以压缩文字或触控区域换取单屏；错误与待核对信息必须可完整查看。原始 HTML 稿保留早期信息结构，最新布局以原生截图及 layout-qa.md 为准。

首次安装手表显示“在 iPhone 登录”，不假装能远程打开任意手机页面。手机 Norr 在登录后恢复车辆读取、切车及授权续期时自动同步；提供“同步到 Apple Watch”入口用于重试或恢复暂停。清除手表授权后暂停自动同步，避免下次读取立即重新授权。首版是需要 iPhone 首次配置的配套 App，不等同于支持完全独立安装和注册的 watch-only App。

同步包应包含协议版本、账号身份摘要、会话版本、必要授权及有效期、当前 VIN、车型及外观配置。凭据仅保存到各自设备的 Keychain，不能存到 Widget 的共享快照、普通 UserDefaults、日志、图片或导出备份。iPhone 和 Watch 没有自动共用的一份 Keychain。

| 情况 | 约定 |
| --- | --- |
| access token 有效 | 手表可尝试请求，仍以服务端授权结果为准 |
| 手机可通信且有更新会话 | 同步更高版本的会话，忽略旧包 |
| access token 过期 | 只在已验证续期方案下尝试续期，否则提示回到 iPhone 更新登录态 |
| refresh token 多端使用 | 验证设备绑定、轮换与旧凭据失效规则；未验证前不宣称两端可独立续期 |
| 切换账号或车辆 | 单调递增版本；请求与回包绑定账号、VIN 和版本，丢弃旧回包 |
| 退出登录 | 清除本机授权及快照，发送清除事件；对端离线期间不能声称已立即远程清除，重连优先应用退出版本 |
| 收到旧缓存 | 保留原始 reportedAt / observedAt，不因为同步就更新数据时间 |

状态数据复用现有 Snapshot 的逐项成功、失败与缺失表达。电量、续航、门锁、空调分别保留观测时间；部分读取失败时，仍显示成功部分，并标注失败或缓存部分。空值不显示为 0%、0 km 或“已关闭”。

## 车控共用约定

门锁与空调使用同一执行和确认模型。首版同一车辆一次只允许一条待完成写入，发送中、等待回读或结果不明时禁用其他写入，并提供“查看待完成操作”。结果确认后可“查看操作结果”，确认返回后再操作。离开页面不丢弃记录；进入原功能页可恢复核对。页面导航不会撤销已经提交的命令。

请求绑定动作、目标值、账号版本和 VIN。切换车辆或账号后保留原请求的归属，不将其显示成新车辆结果，不自动重发；账号退出后的记录不得继续携带凭据。实际 App 的持久化恢复仍需原生验证。

## 门锁命令状态机

1. 从概览的“门锁”进入，展示已锁定、已解锁或未知，以及门锁自己的观测时间。锁态未知或只有过期缓存时，先读取状态，不能把空值当成已解锁。
2. 已锁定时提供“解锁车辆”，已解锁时提供“锁定车辆”。分别检查服务返回的 `supportsUnlock` / `supportsLock` 与账号授权，不能因一种动作可用推断另一种可用。权限不足、明确不支持、能力未确认分别解释；合法共享账号按服务返回处理。
3. 两种动作都先进入确认页，显示车辆名称与动作；若车辆名称重复，补充可区分的 VIN 尾号。HTML 的唯一示例车辆为 Polestar 2。点击“确认解锁 / 确认锁车”才发送；取消、返回或 Escape 在发送前不产生指令。
4. 解锁确认文案说明车门可从车外打开；锁车确认说明将锁定目标车辆车门。表盘组件仍只进入 App，不从组件、通知或离线队列直接执行门锁写入。
5. 确认后冻结本次目标与动作，提交一次 `unlock` / `lock`，进入发送和服务已接收状态。服务回执不直接更新首页锁态，不把超时当作未执行。
6. 独立读取 `exterior.locked`。只有足够新的车辆观测与目标一致，才显示“车辆已解锁 / 已锁定”并更新门锁时间及概览。判定复用 `confirmation.rs` 的请求时间和状态语义，不能使用手机同步到达时间代替车辆观测时间。
7. 回读不一致时展示真实锁态及时间；只有旧读数、读取失败或请求超时时保留“结果待核对”。“核对车辆状态”只读，不再次发送。结果不明时不开放相反指令，也不自动重锁。
8. 完全离线、登录失效、无权限或能力未确认时不提交。网络恢复后由用户重新进入操作，不在后台补发取消或离线期间的请求。服务明确拒绝且确认未执行时显示拒绝原因，不伪造成功。

## 空调命令状态机

首版以用户当前 Norr 的交互为准：开启时使用默认舒适温度 22 °C，不提供手动温度选择或运行中单独改温度。协议中存在的条件调温能力不等于当前车辆已开放该功能，不能据此在手表展示加减按钮。未来若要加入调温，需确认逐车能力、范围及非默认温度的实车执行，再另行评审。

1. 进入空调页，展示运行状态、默认舒适温度及实际观测的座舱温度。默认 22 °C 是启动设定，不能当作车辆已经达到的实测温度。
2. 点击“开启空调”或“关闭空调”提交一次。开启沿用当前 Norr 默认路径，业务命令不附加用户选择的温度（`Command.value=None`），现有协议适配器编码默认 22 °C。请求绑定 VIN、账号版本、动作和本地 requestId，界面锁定重复提交。
3. 请求已发出但未收到确定结果：显示“正在发送”或“结果待核对”。超时不是失败证据，不立即重试。
4. 厂商回执接受或完成后显示“服务已接收，正在核对车辆”，仍不显示“已开启”。
5. 对空调项目做独立读取，按现有默认启动的确认语义核对运行状态与观测时间，满足条件后显示“空调已开启 / 已关闭”。回读目标温度只在实际返回时显示；不能用默认请求值填补缺失回读。
6. 回读缺失、时间较早或不一致，保留“结果待核对”及真实观测。用户可“核对车辆状态”，该动作只读，不重新发送命令。
7. 服务明确拒绝且确认未执行时显示具体原因；权限不足、能力未知、明确不支持分别表达。

本地 requestId 用于追踪和防重复，不代表厂商已经提供幂等保证。若未来加入手机 App 中转，同一命令只允许一个执行端拥有提交权。

## 视觉继承和素材

Design Read：面向 P2 车主的 watchOS 车辆工具，采用 Norr 已确认的极星视觉，ENERGY 2 / RHYTHM 2 / MOTION 1。

- 拉丁文字和数字复用 Archivo Regular，中文使用系统黑体。保持常规字重，以字号、位置和间距建立层级。
- 手表使用现有深色背景 #000000、正文 #EEEFE9、辅助文字 #B0B5AA、暖橙 #F38446；活动控制色 #FF8000，深色字 #20221F。
- HTML 评审画布使用现有浅色底 #F7F7F5，与黑色手表内容区分。手表不新增独立主题切换，深色是 watchOS 小屏与既有 Norr 主题的明确选择。
- 车图原样复用 P2 Long range Dual motor / Snow / black side-cutout.webp。保留车身比例，不重绘、不用生成图替代。
- 概览以车图、电量和续航为重点；空调以温度和单一操作为重点；充电以电量进度和少量数值为重点。
- 门锁页聚焦实际锁态，确认页聚焦目标车辆和明确动作；解锁、锁车沿用同一暖橙主操作色，状态不只依赖颜色区分。
- 首页沿用 Norr 的活动状态规则：有效回读为空调 `active` 时空调按钮橙色，门锁 `locked=false` 时门锁按钮橙色；二者独立，均满足时都橙色。回读确认关闭或锁定后恢复深灰，不能在点击、发送或服务接收时提前切换。读取未知、缺失或失败时不能推断活动状态；展示带时间的缓存时必须同时标记缓存，离线时仍不可提交。橙底使用现有 #FF8000 与深色字 #20221F。
- 图标复用当前项目的 Lucide 源资产，避免引入第二套风格。原生实现可映射到现有 WidgetKit 所用 SF Symbols；这一步需再次视觉评审。
- 按钮至少 44 pt 高，返回按钮至少 44 × 44 pt；圆角用于触控区，读数和分隔线沿用直线结构，不把所有内容做成卡片。
- 主稿以 198 × 242 逻辑单位排版，提供 162 × 197 紧凑尺寸预览。页面可垂直滚动，不能靠缩小所有文字适配小表。
- 实现阶段接入 Dynamic Type、VoiceOver、系统安全区和 Digital Crown。HTML 只验证布局及鼠标/键盘交互，不替代 watchOS 真机可访问性验证。

## 实施顺序和验收

### 先完成技术验证

- 在真实 Apple Watch 上验证 URLSession 对中国区服务发现、授权接口、HTTP/2 gRPC 请求帧、服务端流、响应 trailers 和错误映射的适配。现有 tonic 网络层不能直接视为可用。
- 分别验证借手机网络、手表 Wi-Fi、蜂窝、手机联网中断但蓝牙仍连接，以及完全离线。模拟器成功不等同真机成功。
- 验证 token 设备绑定、续期轮换、并发刷新、退出与换账号。未通过前，独立续期列为未实现。
- 验证抬腕、垂腕、App 切换和锁屏后的命令记录与回读恢复。
- 在授权实车环境验证 `lock` / `unlock` 的账号权限、能力字段、明确拒绝、响应丢失、旧读数、回读不一致与车辆最终状态。HTML 演示不作为可控能力证据。

### 再实现原生 App

新增 watchOS target、SwiftUI 界面、URLSession 适配层、Keychain 会话、WatchConnectivity 同步和 WidgetKit 扩展；复用现有协议模型和确认语义。watchOS 10+ 是首版技术基线建议，最终以实际 SDK、目标设备和组件 API 验证确定。

### 模拟器、IPA 与签名

- 支持 Xcode watchOS 模拟器调试；补充 Watch scheme 与模拟器产物，进行布局、状态、默认空调启停及门锁模拟流程检查。配套 iPhone 的同步流程在匹配的模拟器环境验证；真实网络选路、后台行为和实际车控仍须真机验收。现有 HTML 预览不等于原生模拟器版本已经完成。
- 采用配套 App 打包方式：Watch App 嵌入 iPhone App，同一份真机 IPA 交付。预期包层次为 `Payload/Norr.app/Watch/NorrWatch.app`，Watch Widget 扩展归属 Watch App；模拟器产物与真机 IPA 分开构建。
- 签名仍使用 Apple 开发团队、证书与描述文件体系，但 iPhone 主体、Watch App 及各扩展分别管理 Bundle ID、entitlements 和匹配的描述文件。同团队管理不等于所有 target 共用一份 profile。开发 / Ad Hoc 安装需覆盖相应测试设备；本地开发安装按系统要求开启 iPhone 与 Watch 的开发者模式。
- `finalize-ios.mjs` 已扩展到嵌套 Watch `.app` 的签名准备与校验，包含平台、权限和 companion 标识关联检查。完整真机 IPA 的构建和包结构检查已通过；这不等同于真实开发证书签名及手表安装验证。
- 当前自助签名记录只证明 iPhone / iPad 主体和小组件流程。AltStore / 爱思对新增 Watch 包的保留、重签、关联标识、手表安装和续签须单独验收；尚不承诺原流程零改动可用。先以 Xcode 开发签名打通真实 iPhone + Watch，再验收个人重签分发。

| --- | --- |
| 手机未打开 Norr | 手表前台仍能经系统网络访问服务 |
| 手机不在附近 | Watch Wi-Fi / 蜂窝 + 有效凭据可读取；续期按已验证策略处理 |
| 完全离线 | 缓存带原时间，无伪造新读数；车控不能排队后偷偷执行 |
| 空调启动 / 关闭 | 开启使用默认舒适温度 22 °C，无手动调温控件；厂商回执、独立回读、观测时间满足现有确认规则后才宣布成功 |
| 首页活动按钮 | 空调运行与车辆已解锁分别触发对应橙色；关闭、锁定回读后恢复深灰；超时或旧读数不触发乐观变色 |
| 解锁 / 锁车 | 两种动作均显示目标车辆并二次确认；服务接收时不修改锁态，新观测与目标一致才宣布完成 |
| 门锁取消 / 返回 | 提交前取消不发送，提交后离开页面仍保留请求并可恢复核对 |
| 门锁权限与缺失 | lock/unlock 分别判断；权限不足、明确不支持、能力未确认、状态未知各有说明 |
| 门锁旧回读 / 不一致 | 不宣布完成，显示实际状态或旧读数提示；核对只读，且暂不可发送相反动作 |
| 发送超时 | 不自动重发，能够恢复并只读核对 |
| 共享账号 | 按服务端能力及权限展示；不要求主账号替代合法共享权限 |
| 数据缺失 | 未知、失败、缓存、明确不支持分开显示 |
| 切车 / 换账号 | 旧请求与旧快照不串到新车辆 |
| 表盘 | 缓存与新鲜度可识别，单色可读，点击进入对应 App 页面 |
| 分发 | iPhone + Watch + Widget 的构建、嵌入和签名均独立验证；不沿用现有 IPA 成功作为 Watch 安装证据 |
